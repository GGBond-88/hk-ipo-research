## Code Review Issues

### CR-001: Identical data-fetching logic duplicated across 4 views
- Status: Resolved
- Description: TemporalView (line 18-31), IndustryView (line 18-29), GeographicView (line 18-29), and CrossDimView (line 29-39) each contain the exact same `useEffect` for fetching data and deriving filter options -- approximately 14 lines of identical code repeated 4 times. This violates DRY principle and increases maintenance burden: any change to data fetching or filter option derivation must be made in 4 places. A shared custom hook (e.g., `useDashboardData`) would eliminate this duplication.
- Decision Reason: Created `frontend/src/lib/useDashboardData.ts` shared custom hook that encapsulates data fetching, filter option derivation, loading/error state management, and cleanup (cancellation). All 4 views (TemporalView, IndustryView, GeographicView, CrossDimView) refactored to use the hook, eliminating ~56 lines of duplicated code.

### CR-002: KPI tiles inconsistent with chart data when non-year/industry filters active
- Status: Resolved
- Description: In OverviewView.tsx, the KPI tiles (lines 55-59) filter companies by year and industry only, while the chart data (line 62) applies the full filter state including country, parent, and commitment via `filterCrossDim`. When a user sets a country, parent, or commitment filter from another view and switches to Overview, the chart re-aggregates for the filtered subset, but the KPI tiles (Companies, Total Raised, Needs Review) still show unfiltered totals. This creates a misleading dashboard where the header KPIs and the chart body disagree about what data is being shown. The KPI tile labels give users false confidence about the data scope.
- Decision Reason: Fixed by deriving the set of unique tickers from the fully-filtered cross_dim dataset (`filterCrossDim`), then restricting KPI tile company filtering to only those tickers. This ensures KPI tiles (Companies, Total Raised, Needs Review) reflect the same filtered data scope as the chart, regardless of which filter dimensions are active.

### CR-003: All views swallow fetch errors with no user-facing feedback
- Status: Resolved
- Description: All six view components use `.catch(console.error)` for data fetch failures (OverviewView line 19, CompanyView line 18, TemporalView line 32, IndustryView line 29, GeographicView line 29, CrossDimView line 40). If any data file fails to load, there is zero user-visible feedback: views that check for data before rendering show "Loading..." perpetually (OverviewView line 22), while views without loading guards render with empty data and blank charts. In a production dashboard, silent failures degrade to unusable states without alerting the user or operations team. An error boundary or error state UI should be present.
- Decision Reason: All 6 views now expose error state to users. The 4 views using `useDashboardData` get loading/error state from the shared hook. OverviewView and CompanyView have explicit `loading`/`error` useState with proper cleanup (cancellation flag). Error state renders a red text message. CompanyView additionally shows a warning banner for Sankey fetch failures while keeping company data visible.

### CR-004: CompanyView renders empty filter dropdowns creating confusing UX
- Status: Resolved
- Description: CompanyView.tsx line 41 passes `options={{ years: [], industries: [], countries: [], parents: [], commitments: [] }}` to the FilterBar. This causes the FilterBar to render 5 labeled dropdowns (Year, Industry, Country, Parent, Commitment) that each contain only the "All" option, since no option values are provided. The Company view is intended for per-company Sankey diagram inspection via the ticker picker; the presence of empty filter dropdowns adds visual noise and confusion -- users see filter controls that appear functional but offer no selectable values.
- Decision Reason: Modified FilterBar to filter `DIM_KEYS` by `optionMap[dim].length > 0`, so only filter dimensions with non-empty option lists render dropdowns. When CompanyView passes empty arrays, no filter dropdowns appear -- only the ticker picker and Reset Filters button show. This also benefits any view that lacks certain filter dimensions (e.g., views without geo data won't show Country dropdown).

### CR-005: Chart Y-axis and CSV headers mislabel HKD amounts as percentages
- Status: Resolved
- Description: `src/components/charts/StackedBarChart.tsx` line 37 labels the Y-axis `'% allocation'` and `src/components/charts/TimeSeriesChart.tsx` line 25 labels the Y-axis `'%'`. All five CSV exports across the view components (OverviewView line 49, TemporalView line 46, IndustryView line 42, GeographicView line 48) use headers like `'Growth %'`, `'Financing %'`, etc. However, the data consumed by these charts and exported to CSV is NOT percentages -- it is raw HKD million amounts. The `aggregateByIndustry`, `aggregateTimeSeries`, and `aggregateByGeo` functions in `filterUtils.ts` all sum `amount_hkd_million` from `CrossDimRow` (a monetary field), not `percentage`. Displaying HKD amounts under percentage labels is factually incorrect and misleads users about what data they are viewing.
- Decision Reason: Fixed StackedBarChart Y-axis name from `'% allocation'` to `'HKD Million'`. Fixed TimeSeriesChart Y-axis name from `'%'` to `'HKD Million'`. Fixed all CSV headers in OverviewView, TemporalView, IndustryView, and GeographicView from `'Growth %'` style to `'Growth (HK$M)'` style. Added regression tests in charts.test.tsx verifying correct yAxis.name values.

### CR-006: ScatterChart treats categorical enrichment tag axes as numeric, collapsing all values to zero
- Status: Resolved
- Description: CrossDimView.tsx lines 11-18 define `ENRICHMENT_TAG_KEYS` (`parent_category`, `geo`, `specificity`, `timeline`, `capex_opex`, `commitment`, `esg_tag`) and `ALL_AXIS_KEYS` (3 numeric + 7 categorical). Users can select any of these 10 keys as scatter X/Y axes via the dropdowns at lines 38-51. However, `ScatterChart.tsx` lines 44-45 always creates axes with `type: 'value'`, and the `toNumeric()` helper at lines 14-17 converts string values via `Number(val)`. For all 7 categorical enrichment tags (e.g., `Number("Growth")` = NaN, `Number("committed")` = NaN), `toNumeric()` returns `0` via the `Number.isNaN()` guard. This means all data points collapse to x=0 or y=0 when any categorical key is selected, making the scatter chart completely non-functional for those axis choices. This affects 7 out of 10 available axis options -- the chart silently renders garbage output with no warning. The fix should either make the ScatterChart use category axes for categorical keys, or the CrossDimView should not expose categorical keys in its axis dropdowns.
- Decision Reason: Added `getAxisType()` and `getAxisValue()` helpers to ScatterChart.tsx. `getAxisType()` inspects the first non-null value for a key in the dataset — if it's a `number`, the axis uses `type: 'value'`; otherwise `type: 'category'`. `getAxisValue()` returns raw string values for category axes (with null → 'N/A') and numeric values via `toNumeric()` for value axes. This preserves all 10 axis options in CrossDimView's dropdowns while correctly rendering categorical enrichment tags as discrete labels instead of collapsing them to zero. Added 6 regression tests covering categorical x/y axes, mixed numeric+categorical, null-in-categorical, and all-null-default.

### CR-007: GeographicView computes chart data transformation before loading/error early-return guard
- Status: Resolved
- Description: GeographicView.tsx lines 21-25 compute `geoDataForChart` (iterating over `Object.entries(chartData)` and building a new dictionary) before the loading/error guard on lines 27-28 (`if (loading) return ...`, `if (error) return ...`). This computation is not wrapped in `useMemo`, so it runs on every render even when the view is in loading or error state and will immediately return JSX without using the computed value. On initial mount, when `loading` is `true`, the computation runs unnecessarily and produces a throwaway result. The same pattern applies to `chartData` on lines 16-19, though that one is wrapped in `useMemo`. Either wrapping `geoDataForChart` in `useMemo` or moving it after the early-return guards would avoid this wasted computation.
- Decision Reason: Wrapped `geoDataForChart` in `useMemo(() => { ... }, [chartData])` so the transformation only recomputes when the underlying `chartData` (itself memoized) changes, avoiding wasted computation during loading/error render cycles.

### CR-008: Country filter dropdown populated with geo region names but filter logic checks ISO country codes
- Status: Resolved
- Description: The Country filter is broken because its dropdown options and filter logic operate on different data domains. `deriveFilterOptions` (filterOptions.ts:26) populates the Country dropdown from `Object.keys(byGeo)`, which are geo region names returned by `aggregateByGeo()` (e.g., 'mainland', 'overseas', 'domestic_hk' -- derived from `row.geo`). However, `filterCrossDim` (filterUtils.ts:16-18) checks the selected filter value against `row.countries`, which is documented as "Comma-separated ISO 2-letter country codes" (e.g., 'CN,US'). Since geo region names and ISO country codes occupy different value domains, the Country filter never finds matches -- selecting any country value filters out ALL data rows. This renders the Country filter non-functional across all 5 views that call `filterCrossDim` (TemporalView, IndustryView, GeographicView, CrossDimView, and indirectly OverviewView via the KPI tile ticker derivation). Additionally, `filterOptions.test.ts` line 136 uses ISO codes ('CN', 'US') as GeoData keys in its test fixture, which contradicts the actual runtime GeoData produced by `aggregateByGeo()`, masking this inconsistency in unit tests. The `useDashboardData.test.ts` correctly models geo region names as GeoData keys (line 88-91) and expects those region names in the country filter options (line 150-151).
- Decision Reason: Changed `deriveFilterOptions` to derive country filter options from ISO country codes parsed from `CrossDimRow.countries` (comma-separated ISO 2-letter codes) instead of from `Object.keys(byGeo)` (geo region names like 'mainland'/'overseas'). This aligns the dropdown options with what `filterCrossDim` checks against. Renamed `_crossDim` parameter to `crossDim` (no longer unused) and renamed `byGeo` to `_byGeo` (now unused). Updated `filterOptions.test.ts`: replaced geo-region-key GeoData fixtures with proper geo region names; added tests for trimming whitespace and null handling in countries parsing. Updated `useDashboardData.test.ts` to expect ISO codes ('CN', 'US', 'HK') in country options instead of geo region names. All 181 tests pass.

### CR-009: CrossDimView CSV export shows "0" for null categorical values, inconsistent with chart rendering
- Status: Resolved
- Description: CrossDimView.tsx line 57 constructs CSV rows with `String(r[xKey] ?? 0)`. When xKey or yKey is a categorical enrichment tag (e.g., `esg_tag`, `commitment`, `geo`) and a row has `null` for that field, the CSV exports the string `"0"`. However, ScatterChart.tsx `getAxisValue()` (lines 36-45) returns the string `'N/A'` for `null` values on categorical axes. This means the CSV export and the rendered chart disagree on how null categorical values are represented: the chart labels them as "N/A" (a clear indicator of missing data), while the CSV shows "0" (which users may misinterpret as a valid numeric or categorical value). This inconsistency affects all 7 categorical enrichment tag axis options out of the 10 total axis choices in CrossDimView's dropdowns.
- Decision Reason: Created `frontend/src/lib/crossDimCsvUtils.ts` with `csvValueForCrossDim()` helper that mirrors ScatterChart.getAxisValue() semantics: null on numeric keys (percentage, amount_hkd_million, total_net_proceeds) → '0'; null on categorical keys (enrichment tags) → 'N/A'. CrossDimView.tsx updated to use this helper for CSV row generation. Added 12 unit tests in `crossDimCsv.test.ts` covering all numeric keys, all categorical keys, and edge cases. All 181 tests pass, TypeScript compiles cleanly, build succeeds.
