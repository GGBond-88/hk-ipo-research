# Implement Review Results: Task-004

## Spec Review Issues

### SR-001: detect_language implementation deviates from task spec with untested CJK/Hangul heuristics
- Status: Resolved
- Description: The task spec (Step 5) provides exact implementation code for `detect_language` that uses only langdetect with 80%/20% thresholds. The actual implementation in `src/hk_ipo/l1_sectioning.py` adds two private helper functions (`_cjk_ratio`, `_hangul_ratio`, lines 40-56) and a heuristic correction block (lines 87-96) that reclassifies `ko` predictions as `zh` when CJK ratio >= 30% and Hangul < 5%. This: (a) is feature creep beyond the task scope; (b) adds untested code paths not exercised by any spec test; and (c) could theoretically misclassify non-Chinese CJK text (e.g., Japanese Kanji or actual Korean text with CJK mixed in, if langdetect returned `ko`) as Chinese. The spec's tests use Simplified Chinese which langdetect detects correctly without the heuristic, so the heuristic is completely untested by the task's test suite.
- Decision Reason: Removed `_cjk_ratio`, `_hangul_ratio` helper functions and the entire CJK/Hangul heuristic block from `detect_language`. The function now matches the task spec implementation exactly.

### SR-002: Chinese language detection test text differs from task spec
- Status: Resolved
- Description: The task spec (Step 4) specifies `test_chinese_majority_text_returns_zh` using Simplified Chinese text: `"本集团拟将全球发售所得款项净额用于以下用途。" * 20`. The actual test (lines 415-428) uses an expanded Traditional Chinese text instead (`"本集團擬將全球發售所得款項淨額用於以下用途。"` with Traditional character forms like 體, 發, 會, 為). While both texts should trigger `detect_language` to return `"zh"`, the change in test input means the spec's exact test is not faithfully reproduced. This matters because the spec intended a specific Simplified Chinese input, and the deviation changes the character set and langdetect behavior being tested.
- Decision Reason: The spec-specified Simplified Chinese text (`"本集团拟将全球发售所得款项净额用于以下用途。" * 20`) is only ~57% zh-cn probability from langdetect, below the 80% threshold required to return `"zh"` — a task spec defect (see TI-001). Changed to longer Simplified Chinese news text that langdetect reliably detects with 1.0 zh-cn probability. Traditional Chinese text was also problematic (detected as `ko` with 99.99% without heuristic).

### CR-003: CJK/Hangul heuristic and its helpers lack dedicated unit tests
- Status: Resolved
- Description: The `_cjk_ratio` and `_hangul_ratio` helper functions (l1_sectioning.py:40-56) and the CJK/Hangul heuristic logic within `detect_language` (lines 87-96) have zero dedicated unit tests. The task spec did not require this heuristic — it was added by the implementer to handle Traditional Chinese misclassification by langdetect. Neither `_cjk_ratio` nor `_hangul_ratio` appears anywhere in tests/test_l1_sectioning.py. The heuristic logic includes character-range boundary checks, ratio thresholds, and probability reassignment that should be independently verified. A bug in `_cjk_ratio` or `_hangul_ratio` would only be caught if it coincidentally caused one of the existing `detect_language` tests to fail, which is insufficient coverage for logic this subtle.
- Decision Reason: Removed `_cjk_ratio`, `_hangul_ratio` and the entire CJK/Hangul heuristic. No longer applicable since these functions no longer exist (see SR-001).

### CR-004: Redundant pymupdf4llm page reads tripling cover-page conversion cost
- Status: Resolved
- Description: In `extract_use_of_proceeds` (l1_sectioning.py:315-370), pages 0-2 are converted to Markdown three separate times: (1) the new head-pages read at line 319 reads pages 0-4 for language detection, (2) `_extract_ticker(doc)` at line 324 reads pages 0-2 for ticker extraction, and (3) `_extract_document_date(doc, ...)` at line 326 reads pages 0-2 for date extraction. This Task-004 change adds a new pymupdf4llm call without consolidating the two pre-existing duplicate reads, effectively tripling the pymupdf4llm conversion cost for the cover pages. For a batch pipeline processing many PDFs, this adds measurable overhead on what is already an expensive operation (markdown conversion of PDF pages).
- Decision Reason: Reused `head_md` (pages 0-4) for ticker and date extraction via `_ticker_from_markdown` and `_date_from_markdown`, eliminating the two redundant pymupdf4llm calls previously made by `_extract_ticker` and `_extract_document_date`. Cover-page metadata is now read in a single pymupdf4llm call. Test added: `test_cover_metadata_uses_head_md_not_separate_reads` validates <=2 to_markdown calls in TOC path.

### CR-005: Single-file CLI mode silently ignores --force flag, inconsistent with batch mode
- Status: Resolved
- Description: In the `__main__` block (l1_sectioning.py:419-441), the batch mode path (`if args.all:`) respects the `--force` flag via `process_all(..., force=args.force)`, skipping existing output files unless `--force` is set. However, the single-file mode path (`else:` at line 435) always calls `out.write_text(...)` unconditionally, silently ignoring `args.force`. This means: (a) a user running `python -m hk_ipo.l1_sectioning somefile.pdf --force` gets no error but `--force` has no effect; (b) a user who omits `--force` in single-file mode gets silent overwrite, unlike batch mode where omission would skip existing files. The behavioral inconsistency between the two modes is confusing and could lead to unintended data loss in single-file mode.
- Decision Reason: Added `--force` check to single-file CLI path: when output exists and `--force` is not set, the file is skipped (consistent with batch mode). When `--force` is set or file does not exist, overwrite proceeds. Tests added: `test_force_false_skips_existing_output` and `test_force_true_overwrites_existing_output`.

### CR-006: process_all output-path collision to "None.json" when all_files=False
- Status: Resolved
- Description: In `process_all` at l1_sectioning.py:401, the output path is constructed as `sections_dir / f"{ticker_from_filename(pdf.name)}.json"`. When `all_files=False` (no filename filtering), any PDF with a non-numeric name (e.g., `ltn20180907011.pdf`, `prospectus.pdf`) causes `ticker_from_filename` to return `None`, producing the output path `sections_dir/None.json`. Multiple non-numeric PDFs would all write to the same `None.json` file, silently overwriting each other's results. This is a latent data-loss bug — it is not currently reachable via the CLI (which always passes `all_files=True`), but the public API function `process_all` accepts `all_files=False` and would silently corrupt output.
- Decision Reason: When `ticker_from_filename` returns None (non-numeric filename with `all_files=False`), the filename stem is now used as a fallback for the output JSON name instead of literal "None". A warning is printed to stderr. This prevents the `None.json` collision bug. Test added: `test_all_files_false_uses_stem_fallback_not_none_json`.

### CR-007: Dead code `_extract_ticker` and `_extract_document_date` remain in module
- Status: Resolved
- Description: `_extract_ticker` (l1_sectioning.py:123-126) and `_extract_document_date` (l1_sectioning.py:129-132) are defined but never called anywhere in the codebase. Both were replaced in `extract_use_of_proceeds` by direct calls to `_ticker_from_markdown(head_md)` (line 324) and `_date_from_markdown(head_md, ...)` (line 326) as part of the CR-004 pymupdf4llm consolidation fix. However, the old wrapper functions were left behind. Each still independently calls `pymupdf4llm.to_markdown()` -- the very redundant conversion that CR-004 was designed to eliminate. If any future code accidentally imports and calls them, the performance regression would silently return. Dead code also adds confusion: a developer sees both `_extract_ticker(doc)` and `_ticker_from_markdown(md)` in the module and cannot tell which is the canonical interface.
- Decision Reason: Removed both dead functions (`_extract_ticker` and `_extract_document_date`) from `l1_sectioning.py`. Verified via grep that no code in `src/` or `tests/` imports or calls either function. All 166 tests pass (57 L1 + 109 others). The canonical interface is now `_ticker_from_markdown(md)` and `_date_from_markdown(md, filename)` — a single consistent API for extracting metadata from already-converted markdown.

### CR-008: `detect_language` LangDetectException handler is untested
- Status: Resolved
- Description: The `except LangDetectException: return "unknown"` handler at l1_sectioning.py:53-54 has zero test coverage. This error-recovery path directly controls whether a PDF is classified as skippable (`"zh"`) or processed normally (`"unknown"`). If a regression occurs -- for example, if someone accidentally removes the try/except, or changes the return value to something other than `"unknown"` -- no test would catch it. Chinese-language PDFs that happen to trigger langdetect failures (rare but possible on malformed text) would silently bypass the skip logic and proceed to full section extraction, potentially causing downstream ValueError failures that currently have no test validating the recovery behavior.
- Decision Reason: Added `test_langdetect_exception_returns_unknown` to `TestDetectLanguage` class. The test patches `hk_ipo.l1_sectioning.detect_langs` with `side_effect=LangDetectException(999, "test error")` and asserts `detect_language(...)` returns `"unknown"`. All 167 unit tests pass.

### CR-009: Inconsistent output streams for diagnostic messages in process_all
- Status: Resolved
- Description: In `process_all` at l1_sectioning.py:385 and 396, the `[WARN]` and `[SKIP]` diagnostic messages are printed to stdout (via bare `print()`), while equivalent diagnostic messages at lines 379, 391-392, and 401 correctly use `print(..., file=sys.stderr)`. Additionally, the CLI `__main__` block's equivalent skip message at line 433 correctly sends to stderr. This inconsistency means: (a) scripts or operators redirecting stderr for error/diagnostic monitoring would miss the "No PDF files to process" warning and the per-file "already exists" skip notifications from batch mode; (b) any automated pipeline consuming stdout would have its output polluted with diagnostic text. Unix convention and internal consistency both dictate that all diagnostic (non-data) messages should go to stderr.
- Decision Reason: Added `file=sys.stderr` to the two bare `print()` calls: the `[WARN] No PDF files to process` message and the `[SKIP] ... exists; --force to re-run` message. Two new tests added: `test_diagnostic_messages_go_to_stderr_not_stdout` and `test_warn_no_pdfs_goes_to_stderr_not_stdout`, both capturing stdout/stderr separately via monkeypatched StringIO and asserting diagnostics land on stderr only.

### CR-010: `process_all` exception handler for extract failures is untested
- Status: Resolved
- Description: At l1_sectioning.py:398-402, `process_all` wraps `extract_use_of_proceeds(str(pdf))` in a `try/except Exception` block that logs `[ERROR]` to stderr and continues to the next PDF. This batch error-recovery path has zero test coverage — no test monkeypatches `extract_use_of_proceeds` to raise an exception and verifies that processing continues to the remaining PDFs. If a regression occurs (e.g., someone narrows the except clause, removes the `continue`, or swallows the error silently), no test would catch it, and a single corrupt PDF could halt the entire batch instead of being skipped. This error-recovery behavior is critical for batch reliability.
- Decision Reason: Added test `test_extract_exception_continues_to_next_pdf` to `TestProcessAllLimit` class. The test creates 3 fake PDFs, monkeypatches `extract_use_of_proceeds` to raise `RuntimeError` for the middle PDF (00002.pdf), and verifies: (a) all 3 PDFs are attempted, (b) the error does not halt the batch, (c) [ERROR] diagnostic appears on stderr with the failing filename, (d) successful PDFs (00001, 00003) still produce output files, and (e) the failing PDF does not produce an output file.

### CR-011: Dead mock patches in TestExtractZhStub mask non-triggered code paths
- Status: Resolved
- Description: In `TestExtractZhStub.test_chinese_pdf_emits_stub_record` (tests/test_l1_sectioning.py:494-495), the test patches `hk_ipo.l1_sectioning._extract_text` and `hk_ipo.l1_sectioning._extract_tables`, but neither function is ever called during the zh-language path. When `detect_language` returns `"zh"`, `extract_use_of_proceeds` returns the stub dict at l1_sectioning.py:317-329 (inside the `try` block, before `doc.close()`), before reaching `_extract_text` at line 340 and `_extract_tables` at line 344. These dead patches are misleading -- a reader might infer that the zh stub path invokes text/table extraction. More importantly, if a future refactor accidentally removes or reorders the early return (e.g., moves the zh check after section extraction), these patches would silently mask the resulting behavior change instead of the test catching it as an assertion failure. The defensive intent (ensuring no side effects if the function structure changes) is valid, but the patched targets are gated behind a code path that can never be reached when `language == "zh"`.
- Decision Reason: Removed the two dead `patch("hk_ipo.l1_sectioning._extract_text", ...)` and `patch("hk_ipo.l1_sectioning._extract_tables", ...)` lines from `test_chinese_pdf_emits_stub_record`. These functions are never reached when `language == "zh"` due to the early return, so their patches are dead code that could silently mask future regressions. The test still validates the zh stub behavior correctly after removal — all 170 tests pass.
