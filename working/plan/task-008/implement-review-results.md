## Spec Review Issues

### SR-001: load_golden_fixture has different signature and behavior from spec
- Status: Don't Fix
- Description: The task spec (Step 4, line 245-258) defines `load_golden_fixture(data: dict[str, Any]) -> dict[str, Any]` which accepts a pre-loaded dict and returns a filtered view extracting only `use_id`, `parent_category`, `main_category`, and `sub_category` from each use. The actual implementation defines `load_golden_fixture(path: Path) -> dict[str, Any]` which accepts a file path, reads JSON from disk, validates the `uses` key, and returns the full raw dict. This is a completely different contract. The task spec version is a data-filtering helper; the actual version is a file I/O loader. The A4.5 integration test (Step 9) bypasses this function entirely and uses `json.loads` directly, so the acceptance test does not exercise the changed function. The unit tests in `TestGoldenFixture` test the actual implementation, not the spec.
- Decision Reason: Tried: (1) Change signature to dict-based per spec - 4 tests fail with AttributeError because callers pass Path objects (test_golden_fixture_loader, test_load_golden_fixture_file_not_found, test_load_golden_fixture_malformed_json, test_load_golden_fixture_missing_uses_key). (2) Create new function with spec signature alongside existing - introduces code duplication and confusion between two nearly-identical functions. (3) Rewrite both implementation and all 4 tests - violates task directive "Make all tests from Task 007 pass" (tests define the contract). Resolution: the path-based implementation is richer (handles file I/O, validates input, provides useful errors) and the tests were written for it.

- Decision Reason: Tried: (1) Change return type to list[str] per spec - 2 tests fail (test_parent_sum_exceeds_tolerance_flags, test_main_sum_exceeds_tolerance_flags) because they assert `isinstance(v, dict) and v.get("type") == "parent_sum_violation"`. (3) Hybrid approach returning both formats - overcomplicates a simple validation function with dual-format logic. Resolution: the dict format is richer (structured type, message, metadata) and the tests explicitly validate it.

### CR-002: `validate_parent_sums` validates pre-rebalance original breakdown in `categorize_one`
- Status: Resolved
- Description: At `src/hk_ipo/l4_categorize.py:465`, `categorize_one` calls `validate_parent_sums(parent_breakdown, tolerance=0.5)` using the unadjusted `parent_breakdown` rather than `adjusted_breakdown`. While this is currently mathematically equivalent because `rebalance_layer` and `validate_parent_sums` share the same 0.5% tolerance, the coupling is fragile. If anyone changes one tolerance without the other, the validation would silently diverge from the rebalanced state. A clearer design would validate against the final (adjusted) breakdown, making the dependency on matching tolerances explicit.
- Decision Reason: Fixed. Changed `categorize_one` to pass `adjusted_breakdown` to `validate_parent_sums` instead of `parent_breakdown`. This ensures validation checks the final rebalanced state; within-tolerance deltas that were auto-corrected by rebalance_layer are no longer unnecessarily flagged.

### CR-003: No-op `setdefault`/`pop` pattern in `build_categorized_output`

Related to SR-005 but distinct: SR-005 covers the missing-default-`{}` gap when the key is absent; CR-003 covers the fact that when the key IS present, the code is a no-op.
- Decision Reason: Fixed. Replaced with unconditional `output["extraction_metadata"] = output.pop("extraction_metadata", {})` per spec, which guarantees the key always exists (defaulting to `{}` when absent) and removes the dead-code no-op.

### CR-005: Duplicate sub-proposal filtering logic between `categorize_one` and `process_single`
- Status: Resolved
- Description: `categorize_one` (lines 419-420) uses `record_sub_proposal` which checks `sub and parent in taxonomy and main and main in taxonomy[parent]`. `process_single` (lines 522-525) uses a different filter: `u.get("parent_category") in PARENT_TREE and u.get("main_category") in PARENT_TREE.get(...)` followed by a membership check. - Decision Reason: Fixed. `process_single` now uses `result.get("sub_proposals", [])` from the output (made available by CR-004 fix), eliminating the duplicate filtering logic entirely. Both paths now use the same proposals as computed by `categorize_one`.

### CR-007: `categorize_one` crashes with unhelpful `KeyError` on malformed LLM response

### CR-008: `_tiebreak_key` produces `ValueError` for non-ASCII characters
- Status: Resolved
- Description: At `src/hk_ipo/l4_categorize.py:54`, `chr(0x7F - ord(c))` computes a sort key by inverting ASCII positions. For characters with `ord(c) > 127` (e.g., CJK characters, accented Latin, emoji), the subtraction produces a negative number, causing `chr()` to raise `ValueError: chr() arg not in range(0x110000)`. While the current taxonomy in `taxonomy.py` uses only ASCII English category names, any future addition of non-English category names to `PARENT_TREE` would cause `rebalance_layer` to crash at runtime with an obscure error.
- Decision Reason: Fixed. Updated `_tiebreak_key` to handle non-ASCII characters by mapping them to a safe range above 0x80 (`chr(0x1000 + (cp % 0xEFFF))`), preserving ordering among non-ASCII names while preventing ValueError for codepoints above 127. ASCII path unchanged.

### CR-010: `process_single` crashes with `JSONDecodeError` on corrupted cached output
- Status: Resolved
- Description: At `src/hk_ipo/l4_categorize.py:522`, when `force=False` and the cached output file exists, `json.loads(out_path.read_text(encoding="utf-8"))` is called without any error handling. ### CR-011: `build_categorization_prompt` uses bare dict key access for `use_id`, inconsistent with defensive pattern in `categorize_one`

### CR-014: UTF-8 BOM breaks deduplication in `append_sub_proposals_csv` when reading real `data/taxonomy_proposals.csv`
- Status: Resolved
- Description: The PowerShell command in Step 3 of the task spec (`Out-File -Encoding utf8`) creates `data/taxonomy_proposals.csv` with a UTF-8 BOM (byte sequence `EF BB BF`, confirmed via raw byte inspection). At `src/hk_ipo/l4_categorize.py:230`, the file is opened with `encoding="utf-8"`, which does NOT strip the BOM on read. As a result, Python's `csv.DictReader` sees the first column name as `﻿proposed_label` instead of `proposed_label`. The deduplication check at lines 233-236 (`row.get("proposed_label", "")`) then returns `""` for every row since the actual key is `﻿proposed_label`. This means the `existing` set is always empty when reading the real file, and duplicate proposal rows are appended on every pipeline run. None of the existing tests catch this because they create test CSV files via Python's `write_text()` (no BOM), not via PowerShell.
- Decision Reason: Changed `encoding="utf-8"` to `encoding="utf-8-sig"` on line 230 in `append_sub_proposals_csv` read path. Added test `test_output_appends_to_existing_csv_with_utf8_bom` that creates a CSV file with UTF-8 BOM, appends duplicate proposals, and verifies they are correctly deduplicated. All 46 tests pass.
