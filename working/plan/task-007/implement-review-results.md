### CR-002: Ambiguous violation type assertions fail to pin down API contract
- Status: Resolved
- Description: `tests/test_l4_categorize.py` lines 190 and 220 use `any("parent_sum_violation" in v for v in violations)` and `any("main_sum_violation" in v for v in violations)` respectively. If violations are dicts, `in` tests dictionary _keys_ -- not a dedicated `type`/`code` field. If violations are strings, `in` does substring matching which could produce false positives. Either way, the assertion does not unambiguously define the return type contract for `validate_parent_sums` and `validate_main_sums`. The implementer in Task 008 has no clear guidance on whether violations should be strings, dicts, or dataclasses. The sibling rebalancing tests return dicts (with a `"layer"` key) for rebalanced entries, suggesting violations should similarly use structured dicts with an explicit type field, but the test doesn't enforce this.
- Decision Reason: Updated assertions to require violations be dicts with a `"type"` key (e.g., `isinstance(v, dict) and v.get("type") == "parent_sum_violation"`), matching the structured-dict pattern used by sibling rebalancing tests.

### CR-005: No test for `rebalance_layer` with over-target sums (negative delta)
- Status: Resolved
- Description: All 7 rebalance tests at `tests/test_l4_categorize.py` lines 80-171 use allocations whose sum is <= the target (100 default or a custom target). Financial data can have over-estimated percentages (sum > 100%). There is no test for the case where allocations sum to, say, 105% against a 100% target. The implementer has no guidance on whether `rebalance_layer` should subtract from the largest sibling (negative delta), reject the input, or leave it out-of-scope for another function. This is a real edge case that the closed taxonomy's sum-constraint must handle.
- Decision Reason: Added two tests: test_rebalance_negative_delta_within_tolerance (sum=100.5, delta=0.5 within tolerance, largest sibling absorbs -0.5 to reach 100.0) and test_rebalance_negative_delta_exceeds_tolerance (sum=108.0, delta=8.0 >> 0.5, returns unchanged). This establishes the contract that rebalance_layer handles negative deltas symmetrically: within-tolerance surplus is subtracted from the largest sibling; exceeding-tolerance surplus is flagged (no rebalance).

### CR-006: Tolerance "passes" tests use delta=0 only -- never exercise non-zero within-tolerance path
- Status: Resolved
- Description: `test_parent_sum_within_tolerance_passes` (line 175) and `test_main_sum_under_parent_within_tolerance_passes` (line 197) both use inputs where the sum exactly equals the target (delta=0). A delta of 0 passes regardless of the tolerance value, so the tolerance comparison logic is never actually exercised by these tests. The "within tolerance" path for a non-zero delta (e.g., sum=99.7 vs target=100, tolerance=0.5) is untested. Only the "exceeds tolerance" tests exercise the tolerance parameter (and only the failure path). The implementer could hard-code an exact-sum check and these tests would still pass, defeating the purpose of the tolerance parameter.
- Decision Reason: Updated both test inputs to use non-zero within-tolerance deltas. test_parent_sum_within_tolerance_passes now uses sum=99.7 vs target=100 (delta=0.3 < 0.5). test_main_sum_under_parent_within_tolerance_passes now uses main sum=64.8 vs parent=65.0 (delta=0.2 < 0.5). This forces the implementation to actually compare abs(delta) <= tolerance rather than just checking delta == 0.

### CR-007: `append_sub_proposals_csv` only tests creation, never the append path
- Status: Resolved
- Description: `tests/test_l4_categorize.py` lines 343-359: the function is named `append_sub_proposals_csv` and its purpose is to support idempotent re-runs (the pipeline may re-execute L4 on the same data). Yet the only test creates a fresh file in an empty tmp_path directory. There is no test that: (a) writes an initial CSV with header+row, (b) calls `append_sub_proposals_csv` a second time, and (c) asserts no duplicate header, data rows appended after existing ones, and correct total row count. If the implementer only implements new-file creation, the test passes but the append path is untested and will fail in production on re-run.
- Decision Reason: Added test_output_appends_to_existing_csv which calls append_sub_proposals_csv twice on the same file path: first with an initial proposal row, then with an additional row. Asserts 3 total lines (1 header + 2 data rows), header appears exactly once, and both data rows are present in order. This exercises the true append path required for idempotent pipeline re-runs.

### CR-009: Mismatched-size dict boundary not tested for compute_main_category_match_rate
- Status: Resolved
- Description: `test_match_rate_empty` (lines 498-501) tests `compute_main_category_match_rate({}, {})` -> 1.0 (vacuously true). However, no test covers mismatched-size dicts where one is non-empty and the other is empty, such as `compute_main_category_match_rate({"use_001": {...}}, {})`. Both establish that mismatched sizes return 0.0, avoiding division-by-zero or other undefined behavior.

### CR-010: No error-path tests for load_golden_fixture after CR-004 contract change
- Status: Resolved
- Description: After CR-004 changed the `load_golden_fixture` contract to accept a file path (written to `tmp_path` via `json.dumps` on line 470), the only test (`test_golden_fixture_loader`, lines 454-473) covers the happy path. No tests cover error cases: (a) file not found -- should the function raise `FileNotFoundError`, return `None`, or return an empty dict? (b) malformed JSON -- should it raise `JSONDecodeError` or wrap it? (c) file exists but missing the `"uses"` key -- should it raise `KeyError` or return a default? Without these tests, the implementer may skip error handling, leading to unhandled exceptions when the pipeline encounters corrupt or missing golden-fixture files at runtime. Every file-I/O function in a production data pipeline should have its error contract specified.
- Decision Reason: Added three error-path tests: `test_load_golden_fixture_file_not_found` (raises FileNotFoundError), `test_load_golden_fixture_malformed_json` (raises JSONDecodeError or ValueError), and `test_load_golden_fixture_missing_uses_key` (raises KeyError or ValueError). This establishes that load_golden_fixture must validate its input and raise structured errors, not silently return defaults.

### CR-011: No error-path or edge-case tests for parse_args
- Status: Resolved
- Description: `TestCLIParseArgs` (lines 506-525) tests exactly four happy-path scenarios: `--all` flag, single positional file, `--limit N`, and `--model X`. No tests cover: (a) non-integer `--limit` value (e.g., `--limit abc` -- should it raise `argparse.ArgumentError`, `SystemExit`, or silently coerce?), (b) conflicting flags such as `--all data/extracted/01234.json` where a positional file may conflict with `--all`, (c) missing required arguments if any, (d) unknown flags. For a CLI tool that will be invoked by batch scripts, unhandled argparse errors produce ugly stack traces. The spec says "Each stage is independently runnable" -- robust argument parsing is table stakes.
- Decision Reason: Added three error-path tests: `test_limit_non_integer_raises_system_exit` (non-integer --limit raises SystemExit), `test_unknown_flag_raises_system_exit` (unknown flag raises SystemExit), and `test_no_arguments_raises_system_exit` (no args raises SystemExit). These establish that argparse default error handling (SystemExit) is the expected contract -- the CLI does not silently coerce or ignore bad input.

### CR-012: append_sub_proposals_csv behavior with empty proposals list untested
- Status: Resolved
- Description: `append_sub_proposals_csv` is tested with non-empty lists (1-item creation on line 383, 2-call append on line 415), but there is no test for `append_sub_proposals_csv([], csv_path)`. Should an empty list: (a) create a header-only file, (b) skip file creation entirely, or (c) raise a `ValueError`? The pipeline may call this function after a run that produces zero new proposals. If the implementer picks (a) and the downstream CSV reader expects at least one data row, or picks (b) and the file-absence check is missing elsewhere, production behavior is undefined. This edge case is especially likely for the first run on a small dataset that produces only known-vocab sub-labels.
- Decision Reason: Added `test_output_appends_empty_proposals_no_file_created`: empty proposals list must not create a file (no header-only file). This avoids confusing downstream CSV readers that expect at least one data row, while not raising an error (silent no-op for empty input).
