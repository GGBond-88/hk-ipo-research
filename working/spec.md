# HKEX Global Offering — Use of Proceeds Extraction & Analysis Platform

**Spec date:** 2026-05-19
**Status:** Draft for review
**Scope:** Evolve the existing four-layer pipeline into an eight-stage CLI platform plus a React dashboard, processing a pilot batch of 10–50 English HKEX prospectus PDFs end-to-end.

---

## 1. Goal and scope

Build a CLI-driven data pipeline plus interactive dashboard that:

1. Locates the "Use of Proceeds" section in HKEX Global Offering prospectus PDFs.
2. Extracts each use item with the LLM in two passes: a flat extraction followed by a hierarchical classification into a closed three-level taxonomy with strict 100% sum constraints at every level.
3. Enriches each use item with modular, independently-runnable tag tools (geographic, country, industry, specificity, timeline, capex/opex, ESG, commitment strength).
4. Stores everything in a normalized SQLite database keyed by HK ticker.
5. Pre-bakes JSON aggregates and serves them through a React + Vite + ECharts dashboard with Sankey, time series, heatmap, scatter, and filtered table views.

### Scope decisions baked in

- **Volume:** pilot batch of 10–50 PDFs.
- **PDF source:** manual drop into `data/raw_pdfs/`. No HKEX scraping in this spec.
- **PDF naming convention:** filename is the zero-padded 5-digit HK ticker (e.g., `01234.pdf`). L1 derives `hk_ticker` from the filename. PDFs that do not match the pattern are skipped with a warning.
- **Language:** English only. Chinese-dominant PDFs are detected at L1 and skipped with a stub record; bilingual support is out of scope.
- **Existing code:** evolve in place. Keep the `src/hk_ipo/` package, the existing tests, the L1 PDF parsing, and the OpenRouter LLM integration. The current matplotlib L4 is retired in favor of L4 = hierarchical classification; analysis moves to L7 + frontend.
- **Backend at runtime:** none. The dashboard is a static build that reads pre-baked JSON. SQLite is the data of record for the pipeline; the browser never queries it directly.
- **LLM provider:** OpenAI-compatible API via OpenRouter, configurable model. Default `deepseek/deepseek-v4-flash`.

### Explicitly out of scope (YAGNI)

- Automated HKEX scraping / download (covered by a future L0 spec).
- Live backend serving the dashboard or authenticated multi-user features.
- Mobile-responsive UI beyond ECharts defaults.
- Real-time updates — the dashboard is regenerated by rerunning L7 + rebuild.
- Currency conversion beyond surfacing the `fx_assumption` field for non-HKD raises.

### Architectural decisions

- **Two-pass LLM extraction.** L2 stays flat — the LLM extracts use items with raw category strings and percentages. L4 owns the hierarchy and the strict sum constraints. Rationale: independent retry per stage, debuggable failures, and the expensive flat extraction is not redone when only the categorization is wrong.
- **L5 enrichments are independent.** Each tool reads and writes `data/enriched/<ticker>.json`, mutating only its own `enrichments.<dim>` block. Adding a ninth enrichment is a new module, not a schema migration.
- **SQLite as source of truth, JSON as transport.** The dashboard reads pre-baked aggregates from `frontend/public/data/`, never SQLite. Keeps the frontend stateless and shareable as a zipped `dist/`.
- **Idempotency at every stage.** Every CLI honors `--force`; otherwise it skips work whose outputs are newer than inputs and which has a successful row in `pipeline_runs` with a matching `input_hash`. Re-running the whole pipeline on unchanged inputs is a no-op.

## 3. Taxonomy

Four Parent categories (fixed), each with a closed list of Main categories, each with a semi-open list of Sub categories. The LLM (L4) picks Parent and Main from the closed vocabulary; for Sub, it may propose new labels that follow naming conventions, which are captured to `data/taxonomy_proposals.csv` for periodic promotion.

```
Growth
+-- R&D and Technology
|   +-- Core product R&D
|   +-- Platform / infrastructure R&D
|   +-- Clinical / regulatory development         (biotech)
+-- Product Development
|   +-- New product launches
|   +-- Product enhancements
+-- Sales and Marketing
|   +-- Brand and advertising
|   +-- Channel expansion
|   +-- Customer acquisition
+-- Capacity Expansion
|   +-- New manufacturing facilities
|   +-- Capacity upgrades to existing sites
|   +-- Equipment and machinery
+-- Geographic Expansion
|   +-- Overseas markets
|   +-- Mainland China expansion
|   +-- Specific region build-out                 (e.g. ASEAN, EU)
+-- Acquisitions and Strategic Investments
|   +-- M&A
|   +-- Minority strategic investments
|   +-- Joint ventures
+-- Infrastructure and Network
    +-- Stores / branches
    +-- Data centers and IT infrastructure
    +-- Logistics and supply chain

Financing
+-- Debt Repayment
|   +-- Bank loan repayment
|   +-- Bond / note redemption
+-- Refinancing
+-- Interest Payments

Working Capital
+-- General Working Capital
+-- Inventory Procurement
+-- Receivables / Payables Management
+-- Day-to-day Operations

Others
+-- General Corporate Purposes
+-- Reserves / Contingencies
+-- Unallocated / Unspecified
```

### Sum-constraint rules (enforced by L4)

1. **Parent layer:** sum of all Parent allocations = 100.0% +/- 0.5%.
2. **Main layer:** for each Parent with non-zero share, sum of its Main children = 100.0% of that Parent's share +/- 0.5%.
3. **Sub layer:** for each Main with Sub items, sum of Sub children = 100.0% of that Main's share +/- 0.5%. A Main without Sub items is permitted; it does not "lose" the constraint, it just has no Sub layer.
4. **Tolerance handling:**
   - **Delta <= 0.5%:** auto-rebalance the largest sibling **at the same level under the same parent** to absorb the delta (i.e., a Main-layer violation under Parent `Growth` rebalances the largest Main under `Growth` only; never touches siblings in another Parent or another layer). Record the adjustment in `validation.rebalanced[]`.
   - **Delta > 0.5%:** flag `needs_human_review = true` with reason `parent_sum_violation` / `main_sum_violation` / `sub_sum_violation`. Do not silently rewrite numbers; store as-extracted.

### Enrichment dimensions

Eight dimensions in scope. Each runs as an independent CLI tool.

| Dimension | Cardinality | Example values |
|---|---|---|
| `geo` | per use | `domestic_hk`, `mainland`, `overseas` |
| `country` | per use, list | `CN`, `SG`, `US`, `VN`, ... (ISO 2-letter) |
| `industry` | per company | GICS Industry name (string). Source: LLM read of prospectus by default; `--source manual` accepts a hand-curated `data/industry_overrides.csv` (ticker -> industry) for cases the LLM gets wrong. External classification APIs are out of scope. |
| `specificity` | per use | `specific`, `general`, `vague` |
| `timeline` | per use | `0-12m`, `12-24m`, `24-36m`, `36m+`, `unspecified` |
| `capex_opex` | per use | `capex`, `opex`, `financial` |
| `esg_tag` | per use, optional | `green`, `social`, `governance`, or absent |
| `commitment` | per use | `committed`, `discretionary` |

### 4.2 SQLite schema

```sql
CREATE TABLE companies (
    hk_ticker            TEXT PRIMARY KEY,
    company_name_en      TEXT NOT NULL,
    listing_date         TEXT,
    document_date        TEXT,
    industry_primary     TEXT,
    industry_source      TEXT,
    total_net_proceeds   REAL,                  -- HKD million
    currency             TEXT DEFAULT 'HKD',
    schema_version       TEXT NOT NULL,
    needs_human_review   INTEGER NOT NULL DEFAULT 0,
    review_reasons       TEXT,                  -- JSON array
    updated_at           TEXT NOT NULL
);

CREATE TABLE uses (
    use_id               TEXT NOT NULL,
    hk_ticker            TEXT NOT NULL REFERENCES companies(hk_ticker) ON DELETE CASCADE,
    parent_category      TEXT NOT NULL,
    main_category        TEXT NOT NULL,
    sub_category         TEXT,
    category_raw         TEXT,
    percentage           REAL NOT NULL,
    amount_hkd_million   REAL,
    description          TEXT,
    source_text          TEXT,
    PRIMARY KEY (hk_ticker, use_id)
);

CREATE TABLE use_tags (
    hk_ticker            TEXT NOT NULL,
    use_id               TEXT NOT NULL,
    dimension            TEXT NOT NULL,
    value                TEXT NOT NULL,
    confidence           REAL,
    tool_version         INTEGER NOT NULL,
    PRIMARY KEY (hk_ticker, use_id, dimension, value),
    FOREIGN KEY (hk_ticker, use_id) REFERENCES uses(hk_ticker, use_id) ON DELETE CASCADE
);

CREATE TABLE company_tags (
    hk_ticker            TEXT NOT NULL,
    dimension            TEXT NOT NULL,
    value                TEXT NOT NULL,
    confidence           REAL,
    tool_version         INTEGER NOT NULL,
    PRIMARY KEY (hk_ticker, dimension, value)
);

CREATE TABLE pipeline_runs (
    run_id               TEXT NOT NULL,
    hk_ticker            TEXT NOT NULL,
    stage                TEXT NOT NULL,         -- 'L1'|'L2'|'L3'|'L4'|'L5.geo'|...
    status               TEXT NOT NULL,         -- 'ok'|'skipped'|'failed'|'review'
    input_hash           TEXT,
    output_path          TEXT,
    error_message        TEXT,
    started_at           TEXT NOT NULL,
    finished_at          TEXT NOT NULL,
    PRIMARY KEY (run_id, hk_ticker, stage)
);

CREATE TABLE taxonomy_proposals (
    proposed_label       TEXT NOT NULL,
    parent_category      TEXT NOT NULL,
    main_category        TEXT NOT NULL,
    occurrences          INTEGER NOT NULL DEFAULT 1,
    first_seen_ticker    TEXT,
    first_seen_at        TEXT NOT NULL,
    promoted             INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (proposed_label, parent_category, main_category)
);

CREATE INDEX idx_uses_parent        ON uses(parent_category);
CREATE INDEX idx_uses_main          ON uses(parent_category, main_category);
CREATE INDEX idx_use_tags_dim       ON use_tags(dimension, value);
CREATE INDEX idx_company_tags_dim   ON company_tags(dimension, value);
CREATE INDEX idx_companies_listing  ON companies(listing_date);
CREATE INDEX idx_companies_industry ON companies(industry_primary);
```

**Idempotency contract.** `loader.upsert(record)` runs in a single transaction per ticker: delete all rows from `uses`, `use_tags`, `company_tags` for that ticker, then insert the new rows and upsert the `companies` row. Re-loading the same enriched JSON yields byte-identical DB state.

**Why KV tag tables.** Adding a new enrichment dimension is a code-only change. Aggregate queries do `WHERE dimension = 'X'`, which is well-indexed.

## 5. CLI and tool interfaces

Every stage is independently runnable. Common flags: `--all` (process every file), `<path>` (single file), `--force` (ignore staleness checks), `--limit N` (smoke testing), `--json` (emit a structured run report to stdout).

### Per-stage CLIs

```bash
# L1 — section extraction
python -m hk_ipo.l1_sectioning [--all | <pdf>] [--force] [--limit N]
  reads:  data/raw_pdfs/*.pdf
  writes: data/sections/<ticker>.json
  skips:  Chinese-dominant PDFs (writes stub with skipped=true)

# L2 — flat LLM extraction
python -m hk_ipo.l2_extraction [--all | <section>] [--force] [--limit N]
                                [--model deepseek/deepseek-v4-flash]
  reads:  data/sections/<ticker>.json
  writes: data/extracted/<ticker>.json

# L3 — numeric & vocabulary validation
python -m hk_ipo.l3_validation [--all | <extracted>] [--strict]
  reads/writes: data/extracted/<ticker>.json  (mutates needs_human_review)

# L4 — hierarchical classification
python -m hk_ipo.l4_categorize [--all | <extracted>] [--force] [--limit N]
                               [--model deepseek/deepseek-v4-flash]
  reads:  data/extracted/<ticker>.json
  writes: data/categorized/<ticker>.json
  side-effect: appends to data/taxonomy_proposals.csv when new sub-labels appear

# L5 — enrichment tools (one CLI per dimension)
python -m hk_ipo.enrichments.geo          [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.country      [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.industry     [--all | <categorized>] [--force] [--source prospectus|manual]
python -m hk_ipo.enrichments.specificity  [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.timeline     [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.capex_opex   [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.esg_tag      [--all | <categorized>] [--force]
python -m hk_ipo.enrichments.commitment   [--all | <categorized>] [--force]
  reads/writes: data/enriched/<ticker>.json
                (each tool adds/updates only its own enrichments.<dim> block)

# L6 — SQLite loader
python -m hk_ipo.storage.loader [--all | <enriched>] [--db data/ipo.db] [--dry-run]
  reads:  data/enriched/<ticker>.json
  writes: data/ipo.db  (transactional per ticker)

# L7 — dashboard export
python -m hk_ipo.analysis.export [--db data/ipo.db] [--out frontend/public/data/]
  reads:  data/ipo.db
  writes: companies.json, sankey/<ticker>.json, time_series.json,
          by_industry.json, by_geo.json, cross_dim.json,
          taxonomy.json, manifest.json
```

### Orchestrator

```bash
python scripts/run_pipeline.py [--pdf-dir data/raw_pdfs/]
                               [--workers 6]
                               [--skip L1,L2,L3,L4,L5,L6,L7]
                               [--only L4,L5.geo]
                               [--force]
                               [--limit N]
                               [--dry-run-cost]
                               [--db data/ipo.db]
                               [--build-frontend]
```

Resumability: each stage writes to its own directory; orchestrator skips per-ticker per-stage when output `mtime > input mtime` AND a successful `pipeline_runs` row exists with matching `input_hash`. Failures get an `error_message` row but do not block other tickers.

Cost guardrail: `--dry-run-cost` walks the planned work, sums token estimates against a per-1k-tokens price table in `config.py`, prints the total, and exits without making API calls.

### Shared CLI conventions

- **Stdout:** human-readable progress (`[L4] 01234.pdf ... ok (0.42s, 1,840 tokens)`).
- **Stderr:** warnings only.
- **Exit code:** `0` if all targets succeeded or were intentionally skipped; `1` otherwise.
- **`--json`** emits a structured run report to stdout for programmatic chaining.
- **All stages log** to `data/logs/<run_id>.jsonl` (one line per ticker per stage).

A single global filter state in Zustand: `{year, industry, country, parent, commitment}`. Each view derives its dataset by filtering the pre-baked JSON in memory (50 companies x ~10 uses = ~500 rows, comfortably client-side). Filter changes propagate; charts re-render reactively.

- **Nodes:** `Total Net Proceeds` -> 4 Parent nodes (only those with allocation > 0) -> Main nodes -> Sub nodes.
- **Links:** width proportional to HKD-million amount; node color = parent category color (consistent across all views).
- **Tooltip:** `<percentage>% — HK$<amount>M — <description>`.

## 7. Acceptance criteria

Per component. Each criterion is testable — either a unit/integration test or a concrete observable on a smoke-test corpus.

### L1 — Section extraction

- **A1.1** Given a known-good English HK prospectus PDF, `l1_sectioning` produces `data/sections/<ticker>.json` containing the "Use of Proceeds" section text and any tables found in that section.
- **A1.2** Given a Chinese-dominant PDF, the output JSON has `language: "zh"` and `skipped: true` and no section text; L2+ skips it.
- **A1.3** Given a PDF where "Use of Proceeds" appears as both a section heading and a table-of-contents entry, the extracted section starts at the heading (not the TOC).
- **A1.4** Re-running `l1_sectioning --all` on unchanged inputs produces byte-identical outputs.
- **A1.5** Unit tests cover: language detection thresholds, heading anchor selection, table extraction, missing-section handling (emits warning, not crash).

### L2 — Flat extraction

- **A2.1** For each use item in the source text, L2 emits exactly one `uses[]` row with non-empty `category_raw`, `description`, `source_text`.
- **A2.2** Sum of `percentage` across `uses[]` equals 100.0 +/- 1.0 (existing L3 tolerance).
- **A2.3** When L3 reports a sum violation, L2 self-correction runs at most once with the violation message in the retry prompt; if still failing, the record is flagged `needs_human_review = true` and stored as-is.
- **A2.4** `schema_version` field is present and equals the constant in `schema.py`.
- **A2.5** Existing 130 tests continue to pass.

### L3 — Numeric & vocabulary validation (flat L2 output only)

L3 runs on the post-L2 flat extraction, before L4 assigns the hierarchy. Hierarchical sum rules are enforced inside L4 (see §3 and A4.x), not here.

- **A3.1** Validates `sum(uses[].percentage) == 100.0 +/- 1.0`; violations are recorded in `validation.violations[]` and flip `needs_human_review`.
- **A3.2** Validates `schema_version` is present and equals the constant in `schema.py`; checks `category_raw` is non-empty for every use item; checks `total_net_proceeds_hkd_million` is present.
- **A3.3** Exits 0 with warnings by default; exits non-zero only with `--strict`.

### L4 — Hierarchical classification

- **A4.1** Every `uses[]` row after L4 has non-null `parent_category` and `main_category`; `sub_category` may be null.
- **A4.2** Parent sum = 100.0 +/- 0.5; for each parent, child main sums = parent's share +/- 0.5; for each main with sub items, sub sums = main's share +/- 0.5.
- **A4.3** Auto-rebalance applies only when delta <= 0.5, rebalances the largest sibling at the same level under the same parent (per §3 tolerance rules), and is logged in `validation.rebalanced[]`; delta > 0.5 flags `needs_human_review` without rewriting numbers.
- **A4.4** New sub_category labels not in the closed vocab are appended to `data/taxonomy_proposals.csv` with first-seen ticker and timestamp; the run does not fail.
- **A4.5** Golden-fixture test: a hand-labeled extraction of one real prospectus is checked against expected parent/main assignments; >= 90% main-category match required.

### L5 — Enrichment tools

- **A5.2** Re-running an enrichment tool on the same input produces an identical block (idempotent) unless the tool's internal version bumped, in which case the new block overwrites.
- **A5.3** Each tool has at least one unit test on a fixture covering its key cases (e.g., geo: domestic-only, overseas-only, mixed).
- **A5.4** All eight tools (`geo`, `country`, `industry`, `specificity`, `timeline`, `capex_opex`, `esg_tag`, `commitment`) exist as separate modules under `src/hk_ipo/enrichments/`.
- **A5.5** Removing one enrichment tool from the pipeline does not break the others or the loader (graceful absence).

## 8. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| L4 main-category classification accuracy below 90% on real prospectuses | Reports mislead analysts | Golden-fixture test (A4.5); periodic spot-check of `needs_human_review` queue |
| Sub-category proposals explode (every PDF invents new labels) | Taxonomy churn, broken aggregates | Periodic review of `taxonomy_proposals.csv`; promote frequent labels, retire stragglers |
| Token cost surprises on a 50-PDF batch | Budget overrun | `--dry-run-cost` guardrail (A9.4); per-pdf token logging |
| Sum-constraint auto-rebalance silently corrupts data | Wrong numbers downstream | Strict 0.5% delta cap; full audit trail in `validation.rebalanced[]`; flag-not-fix for > 0.5% |
| Chinese PDFs accidentally enter the pipeline | Garbled extractions | L1 language gate (A1.2); language field surfaced in dashboard |
| Frontend JSON files outgrow client-side filtering | Slow dashboard | L7 can pre-bucket aggregates; not a problem at <= 50 companies |
