# Spec Issues

## SI-001: Rebalance tie-breaking rule unspecified
- **Description**: Spec §3 says auto-rebalance the largest sibling at the same level under the same parent when delta <= 0.5%. Tie-breaking when two or more siblings share the largest percentage is unspecified.
- **Assumption**: Tie-break by alphabetically-first category name (deterministic, reproducible).

## SI-002: industry enrichment `--source manual` failure mode unspecified
- **Description**: Spec §5 says `python -m hk_ipo.enrichments.industry --source manual` uses `data/industry_overrides.csv` (ticker -> industry). Behaviour when the CSV is missing, or when the requested ticker is not in the CSV, is unspecified.
- **Assumption**: Fall back to `--source prospectus` for the missing ticker(s) and emit a stderr warning per ticker; never crash the run.

## SI-003: Frontend filter "year" derivation unspecified
- **Description**: Spec §6.3 says the global filter state includes `year`, but does not say which date field the year comes from (`listing_date` or `document_date`).
- **Assumption**: Prefer `listing_date` when present; fall back to `document_date`; tickers with neither populate a `year = null` bucket excluded from year filters.

## SI-004: SQLite `companies` table lacks `language` column
- **Description**: §4.1 JSON record includes `language` ("en" | "zh" | "mixed"). §4.2 `companies` table schema does not include this column, but §4.2 also says SQLite is the source of truth.
- **Assumption**: Store `language` only in the JSON pipeline output. Frontend never needs it because zh records are stub-skipped at L1 and never reach the DB. The DB has no `language` column; this is not a schema gap.

## SI-005: Manually-passed single PDF that doesn't match `\d{5}\.pdf`
- **Description**: Spec §1 says non-matching filenames are "skipped with a warning". §5 L1 CLI accepts `<pdf>` as a single explicit path. Behaviour for an explicit single path not matching the pattern is unspecified.
- **Assumption**: For `--all`, skip non-matching filenames with stderr warning. For an explicit `<pdf>` path, derive `hk_ticker` from the filename stem if it is 4-5 digits; otherwise process but emit `hk_ticker = null` and add `needs_human_review = true` with reason `unknown_ticker`.

## SI-006: enriched JSON file does not exist yet when first L5 tool runs
- **Description**: Spec §5 says L5 tools "read/write `data/enriched/<ticker>.json`" with each tool only mutating its own block. The first tool to run will find no enriched file.
- **Assumption**: If `data/enriched/<ticker>.json` does not exist, the tool initializes it by deep-copying `data/categorized/<ticker>.json` and adding an empty `enrichments` block, then writes its own block. Subsequent tools merge into the existing file.

## SI-007: `cross_dim.json` shape unspecified
- **Description**: Spec §5 lists `cross_dim.json` as a L7 output but does not define its shape.
- **Assumption**: A JSON array of flat per-use records: `{hk_ticker, use_id, parent_category, main_category, sub_category, percentage, amount_hkd_million, geo, country, industry, specificity, timeline, capex_opex, esg_tag, commitment}`. Used by the Cross-Dim view for client-side filtering and the configurable scatter.

## SI-008: `run_id` source unspecified
- **Description**: Spec §4.2 defines `pipeline_runs.run_id` but does not specify how it is generated.
- **Assumption**: UUID4 generated by the orchestrator at the start of each pipeline invocation (`scripts/run_pipeline.py`). Single-stage CLI invocations generate their own UUID4 per call.

## SI-009: taxonomy_proposals.csv vs taxonomy_proposals table relationship
- **Description**: Spec §4.2 defines a `taxonomy_proposals` SQLite table; §5 says L4 "appends to `data/taxonomy_proposals.csv`". Which is canonical?
- **Assumption**: CSV is the human-editable surface (written by L4). The loader (L6) reads the CSV and upserts the `taxonomy_proposals` SQLite table on every run. Promotion (CSV row -> hard-coded vocabulary in `schema.py`) is a manual code change in a follow-up PR.

## SI-010: Golden-fixture prospectus for L4 A4.5 unspecified
- **Description**: Spec §7 A4.5 mandates a hand-labeled golden-fixture test for L4 main-category match >= 90%, but does not specify which prospectus to use.
- **Assumption**: Use a prospectus already extracted under `data/extracted/` (ticker 3750, file `2025051200005.json`) and hand-label its expected `parent_category` / `main_category` per use item in a JSON fixture under `tests/fixtures/l4_golden/3750.json`. The test is skipped when either the fixture or the extracted source file is missing (parallel to the e2e skip pattern), so the suite remains green on machines without the corpus.

## SI-011: Input hash content for resumability unspecified
- **Description**: Spec §2 "Resumability" says orchestrator skips per-ticker per-stage when a successful `pipeline_runs` row exists with matching `input_hash`. The exact bytes hashed are not defined.
- **Assumption**: For each stage, hash the SHA-256 of the canonical-JSON-serialised input file's bytes (or PDF bytes for L1). Store hex digest.

## SI-012: "Schema SHA" in manifest.json unspecified
- **Description**: Spec §7 A7.2 says `manifest.json` includes "a SHA of the closed taxonomy used".
- **Assumption**: SHA-256 of `json.dumps(CATEGORY_PARENT_TREE, sort_keys=True).encode()` where `CATEGORY_PARENT_TREE` is the closed Parent/Main vocabulary structure in `schema.py`.

## SI-013: Existing `l4_analysis.py` matplotlib code retention
- **Description**: Spec §2 folder layout shows `l4_legacy_analysis.py` (renamed). Spec §1 says the matplotlib L4 is "retired". Whether the legacy file is kept (with no tests) or deleted is implied but not stated.
- **Assumption**: Rename `src/hk_ipo/l4_analysis.py` -> `src/hk_ipo/l4_legacy_analysis.py` with no behavioural changes. Keep `tests/test_l4_analysis.py` running against the legacy module so the 130 existing tests still pass.

## SI-014: Enrichment tool `version` integer semantics
- **Description**: Spec §4.1 says each `enrichments.<dim>` block has a `version` integer. The schema-version-style semantics (bump only when output schema changes, or also when logic changes) is not pinned down.
- **Assumption**: `version` is bumped only when the tool's output schema for that dimension changes in a way that invalidates downstream consumers. Logic-only tweaks do not bump version. The tool reads its current version constant; the loader (L6) uses `tool_version` from the JSON block when upserting `use_tags`.
